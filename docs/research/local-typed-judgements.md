# Local typed judgements

Status: `lab-test` for offline task-type suggestion; reject a default model in the guard or queue. Consumer: `task-sh160-model-disposition` operator and a future task-type evaluator. Owner: KRN maintainer. Verified: 2026-09-29.

## Decision

Keep the deterministic destructive-command guard and human-selected task types. Do not install Laya or another classifier in a live KRN decision path. A model's probability is neither authorization nor permission to drop a check. The bounded offline trial below measured task-type accuracy on historical labels and found a promising **frozen MiniLM encoder plus trained logistic head**, not an earned production benefit. Its 20 test items, label and episode uncertainty, uneven classes and missing human correction costs permit only another independently adjudicated lab test, not adoption. The measured Laya checkpoints are not justified as a default by this trial.

The selected Git-ref task `sh-160` records the local 2026-09-22 Laya 0.3.5 guard comparison: 26 commands, including 14 destructive and 12 benign; the incumbent caught 14/14 destructive with 1/12 benign false positives, while Laya's best wording caught 13/14 with 7/12 false positives. Laya took a measured median 0.66 s per CPU decision, loaded 808 MB of weights and took 69.8 s to load. That local observation rejects **that guard substitution**, not every future model or KRN task-type use. The task record named a held-out task-type trial against the keyword baseline and current triage, including corrections and operation cost, as its falsifier. The successor's trial below measures only offline classification and machine costs, not correction or operating benefit.

## What changed since that measurement

[Laya v0.3.21](https://github.com/NandhaKishorM/laya/releases/tag/v0.3.21) was published 2026-09-27, replacing the evaluated 0.3.5 *software* version. Its [version-pinned README](https://github.com/NandhaKishorM/laya/blob/v0.3.21/README.md#whats-new-in-0321) describes ONNX batch parity, optional INT8 CPU export, an evaluation CLI and opt-in abstention with `min_confidence`. These are candidate operational improvements, **not** evidence that KRN's missed destructive command, false positives, CPU latency or cold load were fixed. Its claimed 33 ms single-question latency is measured on a T4, not this CPU.

The same README's [honest limits](https://github.com/NandhaKishorM/laya/blob/v0.3.21/README.md#honest-limits) report a base checkpoint at 0.362 zero-shot accuracy on the authors' typed-decisions benchmark versus a 0.461 majority-class baseline; 0.766 comes from a checkpoint fine-tuned on that benchmark's training split. It reports wrong high-confidence cancellation choices on narrow negation examples. Its [calibration discussion](https://github.com/NandhaKishorM/laya/blob/v0.3.21/README.md#calibration) says shipped checkpoints are overconfident and need domain temperature fitting. Those upstream benchmark numbers do not transfer to KRN: the small local trial below tests different labels and inputs. `min_confidence` is not a calibrated safety gate by itself.

## KRN offline trial, 2026-09-29

Frozen at merged source `15a783db`, selected queue ref `606d21fb`, dataset SHA-256 `e82561b6f393eecafa9afdbc610fb16850622dc65db910efd31698d86fae4de1`. The input was title plus the first 500 body characters from 107 existing tasks, excluding the newly created successor. A per-type deterministic ID hash made **87 training and 20 test** items; before predictions a title-similarity audit moved one related `refactor` task out of the test. Test support was `bug` 7, `research` 5, `refactor` 3, `task` 3, `decision` 1, `epic` 1. The latter two are individual anecdotes. Historical `Type` values are **not independently human-adjudicated**, and title similarity does not prevent work-episode leakage. All task text remained local in an operator-only host archive under `task-sh160-model-disposition/lab/`; the tracked page contains only aggregates.

Each candidate received those same 20 test inputs. The baseline keyword rule and fastText flags were fixed before test predictions. fastText v0.9.2 trained on 87 labels (`-dim 64 -bucket 20000`, 5.8 MB model); frozen MiniLM revision `1110a243` fed logistic regression (`C=1`) trained on the same 87 labels. Laya 0.3.21 used base revision `55cf4c4e` and externally fine-tuned typed-decisions revision `1a793eb5`, with one fixed six-option `choice` question and opaque A-F labels mapped to the six types. The two Laya checkpoints were **not trained on KRN**. No validation-tuned threshold, prompt search, SetFit fine-tuning or ONNX result was part of the original comparison.

One Ryzen 7 5700U host, four PyTorch/embedding threads, Python 3.12.13, CPU torch 2.14.0. The p95 values come from just 19 warm calls and should not be treated as stable service latencies. The Laya weights were cached for the measured 6.4/9.5 s process loads (first downloads took longer); MiniLM loaded in 6.0 s and trained in 3.5 s. fastText training took 0.35 s. These are small-run timing and peak-RSS observations, **not** full installation, correction, service or operator costs. MiniLM got 7/7 `bug`, 5/5 `research`, but only 1/3 `refactor`, 0/3 `task`, and neither singleton class. FastText chose `bug` 20/20. Laya base made two incorrect predictions above 0.8 uncalibrated confidence. Against the keyword rule, MiniLM gained eight cases and lost two; the paired exact discordance test was `p=0.109` and a descriptive paired bootstrap interval for the 0.30 accuracy difference was `[0, 0.55]`. Several candidates and one small split were examined; **no significance or production uplift is established**.

A **post-hoc operational probe** exported the pinned Laya base through the v0.3.21 ONNX script. It initially failed with `onnxscript` 0.5.4 against torch 2.14.0; `onnxscript` 0.7.2 let the unchanged exporter complete. FP32 ONNX agreed with PyTorch on 20/20 predictions (and got 4/20 correct); INT8 agreed on only **5/20** predictions (and got 5/20 correct), with a 1.63 s warm median and 1550 MiB peak RSS. ONNX Runtime used default threads, unlike the four-thread PyTorch run. This **does not diagnose upstream quantization** or compare controlled backend speed, but it rules out silently substituting this particular INT8 export without parity validation. A one-prompt, one-checkpoint test does not prove that all Laya configurations fail.

## Narrow reopen rule

The tested Laya configurations do not earn deployment, while MiniLM earns at most a **new bounded lab test**. Before promotion, have an operator adjudicate task labels independently, group related work episodes across train/test, enlarge rare types and freeze a larger untouched test with a candidate-independent error/cost bar. Compare the live human/default flow, keyword and selected classifier on actual suggestions, abstentions, correction time, cold load, resident memory and CPU median/p95 end-to-end latency. Keep guard checks and user authority deterministic. If those data are unavailable, defer instead of claiming that 13/20 is a production gain. New upstream releases alone do not reopen the rejection of a default guard model.
