# Make It Sexy

“Sexy” is the operator's shorthand for **finished, coherent, simpler where it
matters, and demonstrably working**. Apply this quality bar to the accepted
change or outcome without asking the operator to repeat it. This skill is a
companion: the current Goal/request, configured task owner and `$delivery-loop`
retain intent, writing, lifecycle and publication authority. It creates no
second status record, gate, store or mandatory subagent team.

## Bind the real target

Read the current request or native Goal, the task if configured, nearest
instructions, HEAD/status, and the affected public caller. Name the base,
working-tree fingerprint or committed head; the source of acceptance; the
intended user/host; and the files and directly affected readers. Preserve other
worktrees. If the requirement or user authority is genuinely ambiguous, stop
that decision and ask one discriminating question; a pretty diff cannot settle
it. A changed spec, source or fixed point invalidates an earlier review.

**Done when:** one owned outcome and an exact review scope are observable,
including what has not been inspected. “Entire codebase” is not the implicit
scope of a small change.

## Discharge the quality bar

For every applicable axis, record a check that can disagree, a verified
finding, or a named evidence/authority gap:

| Axis | Disagreeing signal |
|---|---|
| Intent and behavior | Compare the current user/task requirement with the public result. Exercise a legal case and a realistic failure or revoked-obligation case; agent prose cannot authorize its own scope change. |
| Standards and safety | Apply the repository's instructions and relevant host/security policy at changed call paths; check errors, permissions, data preservation and failure visibility. Prefer a deterministic guard over reviewer confidence. |
| Design and simplification | Use `$codebase-design` when the seam is unclear. Follow caller → interface → result; test whether deleting a wrapper, duplicate rule or speculative layer makes the design deeper without losing behavior. Refactor only where a concrete reader benefits. |
| Proof | Run the fastest owning observer, then required tests and gates at the reviewed fixed point. A new behavioral claim needs executed base-RED/head-GREEN and an independent verifier; 0-budget documentation work reports what its structural check does **not** prove. |
| Knowledge and documentation | Compare affected user docs, skill descriptions, examples, indexes and generated exports with current code and primary sources. Update the owner in place; preserve history and cite a current source rather than copying a transcript. |
| Real use and full cost | Where delivery touches installation, hooks or agent continuation, verify what a fresh host actually loaded; file equality is not that observation. Count retries, workers, review, false blocks, maintenance and rollback before claiming an improvement over unchanged/native work. |

The axes are a **scope-sensitive inspection contract**, not permission to
rewrite every repository page, add six tests, or demand a feature the user did
not request. Existing owners decide procedures: `$code-review` handles fixed
Standards/Spec review; `$source-to-decision` handles external evidence;
`$test-audit` handles test pruning when explicitly in scope. Keep each finding
at its real owner and prefer a small fix or an explicit `reject`/`lab-test`/
`defer` over another layer.

## Use help only where it adds evidence

The current integrator remains the sole writer. When the current owner or
repository contract requires independent review, or a consequential
Standards/Spec unknown survives local checks, ask one bounded read-only
question of a context that did not produce the diff. Parallelize only
independent questions; pin the SHA, spec, files, model, tool rights, deadline
and output contract. Use the operator's current model allowlist and reserve
expensive escalation for a consequential unknown. Verify every finding
locally. More subagents or votes never substitute for the executable check;
provider failures count as cost and unavailable evidence.

**Done when:** each applicable axis is `verified`, `fixed`, `rejected`, or
`blocked/deferred` with owner, reason and next falsifier. Return that compact
disposition to the initiating outcome owner; do not create a parallel report.
After a repair, re-run the affected checks and fixed-point review. Call the
work “sexy” only for the accepted scope with required proofs and applicable
runtime/host checks complete; mark untouched host surfaces not applicable.
Otherwise name the precise remaining blocker without claiming that
uninspected code is perfect.
