# Frontend Discovery

Own the non-mutating analysis outcome. Turn a lawful reference, screenshot, or
existing rendered surface into a compact dossier that separates observation from
inference and gives a later author or reviewer a usable comparator. Stop before
code, target mutation, visual approval, or asset extraction.

Record the source identity and permitted use; observed viewport/state; content
and reading-order inventory; hierarchy; art direction (type, density, imagery,
surface, colour, affordances, and motion); responsive and interaction states;
host constraints; assumptions; unknowns; and the next owner. State missing
intent instead of inventing it.

## Conditional references

- Read [reference analysis](references/reference-analysis.md) when inspecting a
  site, screenshot, or existing surface and deciding what can be claimed.
- Read [direction brief](references/direction-brief.md) when assembling the
  dossier, asking decision-changing questions, or handing it off.

## Composition and boundaries

Compose `grilling` only for a user-owned choice that changes hierarchy,
reference permission, primary action, or acceptance. Compose `research` when a
source fact needs verification, and `prototype` only for a disposable
experiment that can settle one named visual or interaction uncertainty. Those
generic owners retain their procedures. Do not build, edit, approve, run a
visual-review rubric, teach CUBE, or create a frontend-specific alias for any
of them.

Use host code and documented project conventions as the implementation
authority. These references are original decision synthesis from current
primary HTML/WAI material and bounded practitioner, starter, and exemplar
evidence; private vault material is non-distributable, and no reference is a
vendored pattern library or exact API.
